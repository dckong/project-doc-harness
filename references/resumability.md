## 适用条件

满足任意条件时，项目需要显式恢复协议：

- 工作跨越多个会话、窗口或智能体；
- `docs/exec-plans/active/` 中存在活跃计划；
- 本地、测试、预发布和生产状态可能不同；
- 项目已经进入持续部署、运营或外部集成阶段；
- 多条工作流并行，下一动作不能从 Git 历史直接推出。

本文件中的路径均为默认约定；使用 `doc-harness.json` 映射时按实际路径执行同一恢复契约。活跃计划要求项目状态入口，不要求迁移到默认目录。

恢复协议不是新的产品或架构事实源。它提供当前状态和链接，使无记忆智能体无需从长计划、提交记录或聊天中重新推导工作位置。

## 信息半衰期

按变化速度选择所有者和验证方式：

| 类型 | 典型内容 | 维护规则 |
| --- | --- | --- |
| 稳定事实 | 使命、边界、架构职责、已实施决策 | 设计改变时更新，以权威文档和机械约束验证 |
| 活跃状态 | 当前阶段、计划、下一动作、阻塞、技术债 | 任务变化时更新相关计划；影响项目判断时才同步项目摘要 |
| 易变事实 | 部署版本、服务地址、外部依赖、运行配置 | 记录 `observed_at`、环境、验证方法和证据；过期后不得无条件当作当前事实 |

历史记录保留原日期，不按年龄要求刷新。当前文档的复审周期、任务进展日期和运行观测有效期分别维护，具体字段见 [新鲜度契约](doc-contracts.md#新鲜度契约)。

目标、实现和部署是三种不同事实。代码已经实现不证明目标环境已经部署；生产正在运行也不证明它符合最新产品目标。

## 项目状态胶囊

跨会话或复杂项目使用 `docs/PROJECT_STATE.md`：

```markdown
---
doc_type: project-state
status: active
work_status: active
owner: team-or-role
last_reviewed: YYYY-MM-DD
verified_commit: git-commit-or-working-tree-marker
---

# Project State

## Current phase

一句话说明当前阶段。

## Now

只写当前成立的状态摘要并链接权威文档。

## Next action

有计划时链接当前优先计划的 Resume snapshot；无计划时直接写可执行、可验证的下一动作。

## Blocked or awaiting

只列跨任务或影响项目推进的阻塞、依赖对象和决策负责人；任务内部阻塞保留在计划中。已确认没有时写 `None`。

## Active work

按优先级链接活跃计划；已确认没有时写 `None`。

## Environment divergence

只摘要影响项目判断的环境差异并链接运行状态；已比较且没有差异写 `None`，未核实写 `Unknown`，不适用写 `Not applicable`。

## Last verified

有计划或运行文档时链接相关验证记录，只摘要影响项目判断的结论；无计划时直接记录日期、commit 或工作树标识、环境、命令、结果和局限。未验证时写 `Unknown` 并说明原因。

## Decisions and review conditions

链接仍适用的 accepted/implemented/rejected 决策，简述适用前提及哪些新证据、约束或目标变化会触发重审；已确认没有则写 `None`，尚未梳理则写 `Unknown`。
```

保持在约 100 行或 600 中文字以内。项目状态负责项目阶段、工作优先级、跨任务阻塞和任务入口；计划快照负责本任务的下一动作、阻塞与最近验证。没有计划的简单项目可以直接在项目状态中维护这些任务字段。

既有决策的作用是保留判断依据、避免无新证据的重复争论。适用前提改变或出现新证据时，按记录的条件重审，并保留结论变化的理由。旧标题 `Do not reopen` 作为兼容别名保留，不表示永久禁止重审。

工作状态与文档生命周期分开：项目状态文档始终是 `status: active` 的当前入口，`work_status` 描述是否有工作可推进。旧文档省略 `work_status` 时按 `active` 处理；新建时明确填写。

| `work_status` | `Next action` | 其他要求 |
| --- | --- | --- |
| `active` | 优先计划快照的链接，或无计划时的具体动作 | 不接受裸 `None`、`Unknown` 或“继续开发” |
| `waiting` | 解除等待后要执行的动作或计划入口 | `Blocked or awaiting` 说明等待对象，另加 `Resume when` 章节说明解除条件 |
| `idle` | `None` | `Active work` 为 `None`，不存在 active/blocked 计划；另加 `Resume when` 章节说明启动条件，例如“收到有明确范围的新任务” |

等待状态不要求制造现在可做的动作。空闲表示当前没有待执行工作，不应为了填写下一步而擅自新增任务。`Resume when` 必须描述条件，不能只填 `None`、`Unknown` 或 `Not applicable`。恢复协议记录条件，不会自动创建监控或定时任务。

事实字段统一使用：`None` = 已确认没有；`Unknown` = 尚未核实，应说明局限或待核验位置；`Not applicable` = 不适用。未知状态不能写成“无差异”或“已验证”。负责人、下一动作和阻塞解除条件不能靠这些标记替代。

以下变化触发项目状态更新：

- 项目阶段、工作状态、优先级或跨任务阻塞改变；
- 活跃计划创建、关闭或转移，入口需要调整；
- 环境差异或验证结论改变项目层面的判断；
- 新决策或证据改变了既有结论、适用前提或重审条件。

任务内部的下一动作、阻塞细节和验证变化仅更新对应计划；项目摘要已包含的结论若受影响，则在同一次变更中更新摘要。不要求项目状态与每个计划保存相同的验证日期。

## 执行计划恢复快照

每个活跃计划在背景和长日志之前放置：

```markdown
## Resume snapshot

- Current state: 当前已经完成和成立的最小摘要。
- Next action: 下一个可执行、可验收动作；受阻时写解除阻塞后的动作。
- Blocked by: 阻塞和解除条件；没有则写 `None`。
- Awaiting: 等待的人或外部输入；已确认没有则写 `None`。
- Resume when: blocked 计划必填解除条件；active 计划可省略。
- Last verified:
  - commit: commit 或工作树标识
  - environment: local/test/staging/production
  - commands: 实际运行的命令
  - date: YYYY-MM-DD
```

快照是任务级当前状态的主要落点，不替代带日期的 Progress、Discoveries、Decision log 和 Validation。任务变化时更新快照和必要证据；只有影响项目整体判断时才更新项目摘要。`blocked` 计划必须明确阻塞或等待对象、解除条件和恢复后的动作。验证字段尚未核实时允许 `Unknown`，并在 Validation 说明未覆盖范围，不能伪造命令或成功结果。

## 计划关闭事务

计划只有在持久信息拥有新位置后才算完成。`Completion notes` 至少包含：

```markdown
## Completion notes

### Outcome
最终达成或取消了什么。

### Durable decisions promoted
链接已提升的设计决策；没有则说明为什么没有持久决策。

### Product or architecture updates
链接同步后的产品、架构或运行文档；不适用则写 `None`。

### Remaining work transferred
链接新计划或技术债；没有则写 `None`。

### Rejected alternatives recorded
链接仍能防止未来误判的否决理由；没有则写 `None`。

### Final validation
记录 commit、环境、命令、结果和未覆盖范围。
```

关闭顺序：

1. 从 Decision log 和 Discoveries 识别持久知识；
2. 按各自职责更新产品目标、架构与运行事实；已批准未落地的决策记为 accepted，已有落地证据的记为 implemented；不得把实现缺陷提升成产品目标；
3. 将未完成工作转入新计划或技术债；
4. 保存仍有未来防错价值的 rejected alternative；
5. 记录最终验证；
6. 更新 `PROJECT_STATE.md` 和活跃计划索引；
7. 修改计划状态并移动到 `completed/`。

`completed/` 是执行历史，不自动拥有当前产品或架构权威。不能让新智能体必须阅读已完成计划才能理解当前设计。

## 冷启动验收

从根 `AGENTS.md` 开始，沿仓库内记录的入口查阅本地材料或可访问的外部权威来源，不依赖未记录的聊天和个人记忆。外部来源需要注明访问条件；无法访问时保留必要摘要和证据局限。验证新智能体能否在两次跳转内回答：

1. 项目使命和非目标是什么？
2. 当前阶段和已经成立的状态是什么？
3. 当前优先工作是什么；若在等待或空闲，什么条件会恢复工作？
4. 阻塞是什么，由谁或什么条件解除？
5. 当前产品、架构和运行事实的权威来源在哪里？
6. 目标、本地、测试和生产之间有哪些差异？
7. 相关任务或环境的验证记录在哪里，对应哪个 commit、环境、命令和日期；哪些尚未核验？
8. 哪些既有决策仍然适用，它们基于什么前提，哪些新证据或条件变化会触发重审？

任何答案需要从聊天、提交信息或长篇 completed plan 中推断，都说明恢复协议仍有缺口。
